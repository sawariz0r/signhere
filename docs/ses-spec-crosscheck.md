# SES specification cross-check

Source review: 24 September 2026. This maps the supplied ordinary B2B simple electronic signature (SES) development specification to the current implementation. It is an engineering coverage review, not a legal opinion, identity certification, security audit, or claim that every contract type can use this method. See [architecture](architecture.md), [deployment](deployment.md), and the [sealing profile](pdf-sealing-spike.md) for the trust and deployment boundaries.

The scope below is **new evidence-v2 documents**. Existing v1 documents retain their original evidence format and synchronous completion path. They are not silently upgraded or retrospectively sealed.

## Requirement coverage

| Requirement | Current implementation | Assessment / boundary |
| --- | --- | --- |
| Simple signing for ordinary B2B; no eID claim | The `draw` method declares `verifiesIdentity: false`; provider evidence says self-asserted. JSON and the PDF explicitly disclaim eID identity verification, qualified signatures and trusted timestamps. | Implemented technical description. Suitability for particular contracts remains an operator/legal decision. |
| Personal, unpredictable signer/transaction links | `randomBytes(32)` creates a 256-bit capability. Its SHA-256 hash is stored against one recipient and document. Signing intent separately binds installation, document/revision ID, recipient, frozen PDF hash, method/version, consent and a random nonce. | Implemented. Possession establishes access to the invitation, not control of an independently verified identity or email account. |
| Expiry configurable; HTTPS | `SIGNHERE_SIGNING_LINK_TTL_DAYS` accepts integer 1–365, default 7, for new or rotated unsigned links. The configured public origin must use HTTPS except localhost. | Implemented configuration; the operator must correctly configure TLS, proxy trust and cookies. Local tests do not establish public TLS deployment correctness. |
| Revocation | Pending documents can be cancelled; an unsigned recipient's link can be rotated. Separate completed-copy capabilities can be revoked for that recipient by an authorized team account. | Implemented for those capabilities. There is no separate revocation endpoint for an already accepted signer's original receipt capability. |
| Link unusable after signing | A recipient can accept only once. Exact idempotent retries return the existing result; changed submissions fail. The same token continues to open a read-only receipt and download the completed PDF while the document is pending or finalizing, and until at least 30 days after completion. | **Deliberate difference from literal single-use-token wording.** Signing authority is consumed, but the token itself is retained for receipt/lost-response recovery. A distinct receipt-capability exchange is deferred. |
| Freeze exact original bytes/hash; same hash for all signers | The raw upload is retained unchanged. Supported interactive content is flattened before document creation. The prepared file is then frozen as `original` / `originalHash`; every recipient's intent and acceptance bind that hash. Source hash and conversion metadata are immutable. | Implemented with a terminology distinction: recipients approve the **prepared signing copy**, not an unshown pre-conversion file. `uploaded.pdf` is retained separately when different. The raw file is also indirectly bound through the creation evidence. |
| Changed content requires a new transaction | Runtime APIs and database guards reject replacement of frozen bytes, recipients and protection policy. A corrected signing request needs a new document ID. | Implemented. `documentId`, transaction ID and intent revision ID currently identify the same signing transaction; there is no separate multi-revision logical-document entity. |
| Explicit, initially unchecked consent | The signing UI starts unchecked and submits `accepted: true`; the API requires it. Exact consent text/version are frozen in the recipient intent and used for later display/acceptance even if the application default changes. | Implemented. The record is the server's acceptance of affirmative submission, not proof that a human read every word. |
| Consent tied to signer, hash and UTC time | The accepted event contains recipient ID, intended name/email, claimed name, original hash, exact consent, intent bytes/hash, `consentAcceptedAt`, `signedAt`, document/transaction ID and `authenticationMethod: personal_signing_link`. | Implemented in v2. Consent and signature are submitted atomically, so both times are the same server UTC instant; there is no separately tracked browser checkbox-click time. |
| Drawn signature and signing method | Validated vector strokes, method ID/version and provider evidence are recorded in the same transaction as recipient completion and the hash-linked event. | Implemented. This is a participant approval record; the later certificate signature belongs to the installation, not a personal certificate held by that participant. |
| Evidence contains IP and user agent | Signing/open events retain bounded observed request metadata. Trusted proxy configuration controls which IP source is accepted. | Implemented observations, not identity proof. Full private evidence exports require a team session. PDF-only bearer downloads do not expose all signers' request metadata. |
| Append-only audit events | Events are ordered and hash linked. Database guards prevent update/deletion under the restricted runtime role; signed evidence through the last participant approval is frozen and committed by the PDF seal. | Implemented semantic events; see mapping below. A database owner can bypass database guards. Someone controlling the installation key can issue another valid seal. |
| Final PDF contains document plus certificate/evidence pages | The completed PDF contains the prepared document's pages and per-signer appendices: assigned/claimed name, contact, server UTC consent/signing time, method, personal-link authentication, consent, document/transaction UUID and prepared hash, with explicit no-eID assertion. | Implemented content. The PDF writer reserializes the prepared file while adding pages; it does **not** embed the exact prepared file bytes. Exact prepared bytes are exported separately. Source-page rendering equivalence needs broader regression testing. |
| Final PDF SHA-256 | SHA-256 of the exact sealed output is stored with completion and exported separately. `/verify` compares a browser-computed digest with this installation's completed records. | Implemented externally. The PDF cannot contain its own full-file digest without creating a circular dependency. Its protected manifest instead binds prepared hash, evidence-core hash, checkpoint, policy and issuer. |
| Completed immutable and failure-safe | The last acceptance atomically freezes evidence and queues durable finalization. Completion publishes final bytes, digest and completion event together only after sealing/validation. Lease generation fencing prevents stale jobs publishing. Failed finalization preserves approvals. | Implemented for v2. Retrying does not let an operator change participant approvals or silently weaken the frozen policy. Existing v1 completion remains a separate compatibility path. |
| Account authentication and cross-document denial | Team-scoped authenticated lookups protect creation, original uploads, private evidence/ZIP exports and administration. Bearer lookups scope a capability to its recipient/document; responses omit private event data. | Implemented boundary. Independent adversarial security review remains required. Documents are team resources, rather than exclusively accessible to their creator. |
| No raw capability logging | Raw links use URL fragments, are supplied in API bodies, and are not recorded in audit events. Application error logging omits request bodies and secrets. | Implemented application behavior. Operators must ensure reverse proxies, telemetry and support tooling also avoid capturing request bodies or full copied links. |
| Secure storage, backups and minimal personal data | PostgreSQL retains PDFs/evidence; the private key store is separate with restrictive ownership/modes. Paired encrypted off-host backups and restore instructions are documented. Bearer receipts/copies deliver the PDF only; the team can explicitly export private evidence. | Partial operational coverage. Retention/erasure tooling and policy, encrypted disks, actual Docker recovery drills and backup scheduling remain deployment responsibilities/release gates. |
| Future BankID binds signer, transaction and exact hash | Versioned method context already supplies recipient/document/hash/consent. Frozen intents add domain separation, nonce and method version. | Foundation only. BankID/Freja integration, authenticated callbacks, replay protection, persisted provider attempts and provider-result validation are not implemented. |

## Audit-event mapping

The supplied event names describe semantics. The current schema intentionally combines some actions in a single database transaction/event:

| Supplied event | Current evidence | Exact interpretation |
| --- | --- | --- |
| `transaction_created` | `document.created` | Freezes participants, sender assignment, content hash, preparation metadata and protection policy. |
| `signing_link_created` | Recipient creation alongside `document.created`; later `link.rotated` | Initial capabilities are issued in the same transaction as creation. There is no distinct initial per-link audit event or recorded evidence that a link was delivered. Raw tokens are never audited. |
| `signing_link_opened` | First `recipient.viewed` | The bearer signing session was successfully opened. Repeated opens are not separate events. |
| `document_viewed` | Same `recipient.viewed`, followed by authenticated PDF access in the client flow | **Partial.** This is not a separate PDF-response/download event or proof of all-page reading. Do not label it as verified reading. |
| `consent_accepted` | `recipient.signed` with frozen consent and explicit UTC acceptance time | Consent is accepted atomically with the signature submission. |
| `signature_submitted` | Same `recipient.signed` with strokes, method and intent binding | Successful validated submission, not every failed attempt. |
| `signer_completed` | Same event plus immutable recipient acceptance | Exactly one accepted result, with idempotent retries. |
| `transaction_completed` | `document.completed` | Appended only after validated sealed output is atomically published. This event/final file hash are outside the earlier sealed evidence core to avoid a hash cycle. The verifier reports that outer completion metadata as consistency-only. |

Cancellation and unsigned-link rotation also have explicit events. Completed-copy link creation/revocation currently changes capability records without adding events to an already frozen signing evidence chain. An operational security log for post-completion access administration would be a separate feature.

## What independent verification establishes

New v2 output has a PDF/CMS installation seal produced with the maintained pyHanko engine. The default key is unique per installation and self-signed. Optional imported certificate files are supported; no paid certificate or hosted service is needed. The offline verifier checks exact file coverage, CMS cryptography, the protected manifest, canonical evidence and participant/document bindings without contacting the Signhere server.

A valid seal with an unknown issuer is reported separately from a matching independently trusted certificate fingerprint. The certificate bundled with a document cannot establish its own authenticity. No trusted timestamp or revocation check is implemented. The profile targets the relevant PDF/CAdES structures but is not a formal PAdES conformance claim. Platform sealing does not turn personal-link/draw approval into verified human identity, nor prevent a compromised host/key owner from issuing a replacement record.

The public `/verify` page is a convenient installation-local hash lookup, not the offline CMS verifier or an independent trust service. A reader with only the sealed PDF can check its certificate signature using compatible PDF tooling; validating Signhere's full private audit evidence also requires the evidence export from an authorized party.

## Outstanding release checks and review disposition

The requested [Claude Opus 5.5 source critique](reviews/2026-09-24-claude-sealing-code-review.md) and [implementation-design review](reviews/2026-09-24-claude-sealing-implementation-design.md) are retained in the repository. Their findings are review input rather than executed tests. See [implementation status and dispositions](sealing-implementation.md) for follow-up changes; the critique alone does not certify their resolution.

- Execute the Linux image/Compose CI: startup isolation probes, fresh two-party signing, restricted runtime-role checks, restart persistence and paired restore. Docker/WSL execution was unavailable on the development machine. Warning-clean cross-compilation and static YAML checks are not substitutes.
- Exercise malformed and borderline PDF inputs before participant acceptance, and maximum-size strokes, many recipients and concurrent uploads/finalization. Creation now performs a public-certificate dry run through appendix generation and strict seal preparation, and strokes have a 64 KiB serialized cap. These reduce deterministic late failures but do not establish worst-case rendering/size behavior; total RSS and temporary storage need actual measurement. The critique's 64 MiB tmpfs observation is superseded by the current 128 MiB setting; the app-container RSS cap remains 768 MiB.
- Confirm table ownership and forbidden TRIGGER/DDL/TRUNCATE privileges on an actual deployed fresh or migrated database. The bootstrap script was absent from Claude's packet; a separate disposable real-PostgreSQL role test ran locally. Existing volumes need explicit ownership/role migration, not just new passwords.
- Exercise database-ahead/key-backup-ahead restoration and recovery of in-flight finalization around key rotation. Keep identity mismatch fail-closed and preserve accepted approvals.
- Complete independent PDF-reader cryptographic validation and broader source-page rendering equivalence checks. OpenSSL CMS verification and exact candidate/sealed render comparison are useful evidence but do not replace every reader/conformance check.
- Review the native parser boundary independently. The corrected launcher comment acknowledges that pre-exec `PR_SET_DUMPABLE(0)` does not remain set after ordinary exec. Core-size limits, filesystem policy and syscall restrictions are the actual layered controls. The full parent application still holds sealing authority.
- Establish retention/erasure and backup-age policies, storage quotas, incident response, fingerprint distribution/rotation and a suitable legal review before production claims.

Strict destruction of the signing token after acceptance, separate verified document-view events, trusted time, verified eID identity and independently audited deployment are not presented as completed features.
